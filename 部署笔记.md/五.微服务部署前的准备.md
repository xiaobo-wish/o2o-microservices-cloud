### 1.Jar包的交付

```properties
本项目的jar包有十个，都是预构建好的可执行的jar.

有了jar包部署时就不需要我们安装jdk/maven去进行源码编译了。

说明：jar包就是Java归档文件，里面打包了Java程序运行所需的各种文件，可以用`java -jar xxx.jar` 直接运行程序。源码编译的话就是在项目根目录执行`mvn clean package`

每个jar包内同时打包了多套运行配置，profile在运行时选择环境

bootstrap.yml（公共配置）

bootstrap-dev.yml 

bootstrap-test.yml 

bootstrap-prod.yml
```

jar 内置的 bootstrap.yml 默认 spring.profiles.active: dev：

```yaml
bootstrap.yml（片段）
spring:
  profiles:
    active: dev     # 默认 dev！
  application:
    name: jzo2o-foundations
```

生产中必须使用prod，否则请求转发会失败。

```properties
默认 active 是 dev，服务启动会加载 bootstrap-dev.yml，去连写死的开发机 Nacos192.168.101.68:8848的地址——生产集群里要么连不上、要么连到错误地址，服务注册不进集群 Nacos

网关路由是 lb://jzo2o-xxx（按服务名负载均衡），Nacos 里找不到实例，前端请求转发直接失败

所以部署到 K8s 时必须用 prod 覆盖默认值：JAVA_OPTS=-Dspring.profiles.active=prod，并注入 NACOS_ADDR=nacos:8848 等环境变量
```

验证jar包内置的bootstrap文件，**程序启动时最先加载的那个配置文件**，用来初始化环境、加载设置，让程序能跑起来。

```bash
[root@master01 jars]# cd /data/jzo2o-single/12-microservice/jars
[root@master01 jars]# vim jzo2o-foundations.jar
# 预期：4 个文件都打包在 BOOT-INF/classes/ 下
#   bootstrap.yml
#   bootstrap-dev.yml
#   bootstrap-test.yml
#   bootstrap-prod.yml
```

交付的 jar 后续用来编写 Dockerfile，构建镜像；

profile 的选择交给运行环境（K8s env + JAVA_OPTS）在启动时决定。



### 2.编写Dockerfile文件以及镜像的导入

##### 1.10个服务程序jar包的Dockerfile差异只有包名与端口，实例如下

```dockerfile
# 基础镜像：Eclipse Temurin JDK 11（JRE 精简版，Alpine 系统；openjdk:11-jdk 已下架）
FROM eclipse-temurin:11-jre-alpine

# 镜像维护者
LABEL maintainer="传智教育研发组"

# 设置时区为上海，保证日志时间正确
RUN echo "Asia/Shanghai" > /etc/timezone

# 构建参数：jar 包路径（默认 jars 目录下，可用 --build-arg 覆盖）
ARG PACKAGE_PATH=./jars/jzo2o-foundations.jar

# 将 jar 包拷入镜像并重命名为 app.jar
ADD   ${PACKAGE_PATH:-./}   app.jar

# 服务实际监听端口（与 bootstrap.yml 的 server.port 一致）
EXPOSE 11509

# 启动命令：动态拼接环境变量 JAVA_OPTS 指定的 JVM 参数
ENTRYPOINT ["sh","-c","java -jar $JAVA_OPTS app.jar"]
```

$JAVA_OPTS只是一个变量，在这里构建时只是写进镜像的一条启动命令，容器启动时会去找环境变量，通常是这个形式`JAVA_OPTS="-Dspring.profiles.active=prod -Xms512m -Xmx1024m -XX:+UseG1GC"`，最后会拼到Java命令后，`java -Dspring.profiles.active=prod -Xms512m -Xmx1024m -XX:+UseG1GC -jar app.jar`

```bash
[root@master01 12-microservice]# vim build-images.sh
#!/usr/bin/env bash
# ============================================================
# build-images.sh —— 基于 Dockerfile 模板一键构建 10 个微服务镜像
# 前置：
#   1. 10 个 jar 已就绪（./jars/ 目录，见 1.1 Jar 包交付）
#   2. 构建机已安装 Docker，并能拉取 eclipse-temurin:11-jre-alpine
#      （无法直连 Docker Hub 时，把 daemon.json registry-mirrors 配成轩辕镜像源）
# 用法：在 12-microservice 目录执行  bash build-images.sh
# ============================================================
set -e
TAG=1.0.0
# 服务清单：名称:端口（端口与 bootstrap.yml 的 server.port 一致）

SERVICES="
jzo2o-gateway:11500
jzo2o-customer:11502
jzo2o-publics:11503
jzo2o-orders-manager:11504
jzo2o-trade:11505
jzo2o-orders-seize:11506
jzo2o-orders-dispatch:11507
jzo2o-orders-history:11508
jzo2o-foundations:11509
jzo2o-market:11510
"
for entry in $SERVICES; do
  name=${entry%%:*}
  port=${entry##*:}
  echo "=== [$(date '+%H:%M:%S')] 构建 $name（端口 $port）==="
  # 由 1.2 通用模板生成该服务的 Dockerfile（jar 名 + 端口替换进去）
  cat > "Dockerfile-$name" <<EOF
FROM eclipse-temurin:11-jre-alpine

LABEL maintainer="传智教育研发组"

RUN echo "Asia/Shanghai" > /etc/timezone

ARG PACKAGE_PATH=./jars/$name.jar

ADD \${PACKAGE_PATH:-./} app.jar

EXPOSE $port

ENTRYPOINT ["sh","-c","java -jar \$JAVA_OPTS app.jar"]
EOF
  docker build -f "Dockerfile-$name" -t "jzo2o/$name:$TAG" .
done
echo ""
echo "构建完成，本地镜像清单："
docker images | grep "jzo2o/jzo2o" || true
```

2.脚本实现一键导入

```bash
#!/usr/bin/env bash
# export-and-import.sh —— 导出 10 个镜像并分发到 3 个 K8s 节点导入 containerd

# 前置：构建机已用 build-images.sh 构建好镜像；可 ssh/scp 免密访问节点
# 用法：bash export-and-import.sh
set -e
TAG=1.0.0
NODES="<master01内网IP>  <worker01内网IP>  <worker02内网IP>"
# 比如，改成  NODES="172.17.163.242 172.17.163.241 172.17.163.240"
IMAGES="
jzo2o-gateway
jzo2o-customer
jzo2o-publics
jzo2o-foundations
jzo2o-market
jzo2o-trade
jzo2o-orders-seize
jzo2o-orders-dispatch
jzo2o-orders-manager
jzo2o-orders-history
"

OUT=/root/jzo2o-images
for node in $NODES; do
  ssh "root@$node" "mkdir -p $OUT/"
done

for img in $IMAGES; do
  docker save "jzo2o/$img:$TAG" | gzip > "$OUT/$img.tar.gz"
  for node in $NODES; do
    scp -q "$OUT/$img.tar.gz" "root@$node:$OUT/"
    ssh "root@$node" "gunzip -c $OUT/$img.tar.gz | ctr -n k8s.io images import -"
  done
done
```

### 3.服务的依赖关系

微服务之间不是孤立的，必须按依赖顺序部署，否则后面的服务启动时调用不到依赖会一直报错

按三个阶段分批上线，每阶段以可验证的里程碑收口：

1. 阶段一 登录打通（4 个）：foundations → publics → customer → gateway。里程碑：浏览器能登录、首页基础数据正常；发现点：点开"订单管理"菜单 → 接口 502（订单模块未部署）
2. 阶段二 订单主链路（5 个）：orders-manager → orders-seize → orders-dispatch → orders-history → trade；里程碑：订单列表 / 派单 / 历史订单 / 支付可用；发现点：点开"营销管理"菜单 → 接口 502（营销模块未部署）
3. 阶段三 营销闭环（1 个）：market；里程碑：优惠券 / 活动可用，全部 10 个服务注册就绪

从依赖角度看，本质仍是"**依赖先就绪**"：阶段内先起无依赖的基础服务，再起业务服务，网关永远放最后

**为什么要有这个顺序**？

```properties
微服务启动后会向 Nacos 注册自己

如果 gateway 先启动，它会尝试路由到后面还没启动的服务，这时访问会返回 502

同理，orders-seize 先启动而 foundations 还没起，它 Feign 调基础数据会一直 Connection refused

所以上线时按"依赖先就绪"原则：先起无依赖的 foundations，再起业务服务，最后起网关

服务之间通过 Nacos 服务发现，只要都注册成功，顺序错了也不会崩，但日志里会刷一堆 ERROR，排查体验很差
```

# 第一步：解压并导入业务数据库（在任意能访问集群的机器上执行）

##### 3.4 后端 Gateway 占位 Servcie

**先建一个没有真实后端 Pod 的 Service,占住名字/IP/端口,让别的服务能先按这个名字配置,等真正的 Gateway 起来再对上。**

Nginx 启动时会解析 proxy_pass 里的上游域名，如果 jzo2o-gateway 这个 Service 还不存在，Nginx 会直接启动失败（[emerg] host not found in upstream），页面都打不开

```bash
cat > /data/jzo2o-single/11-frontend/gateway-svc.yaml <<'EOF'
---
apiVersion: v1
kind: Service
metadata:
  name: jzo2o-gateway
  namespace: jzo2o
spec:
  type: ClusterIP
  ports:
    - name: http
      port: 11500
      targetPort: 11500
EOF
kubectl apply -f /data/jzo2o-single/11-frontend/gateway-svc.yaml
```

没有selector，就不会往endpoint里面写pod的IP，所以里面是空的，打过去连不上，但是DNS名字jzo2o-gateway . jzo2o能解析，端口能对上。这就达到了占位目的:**让前端/其他服务先能按这个地址配置,不阻塞部署**
