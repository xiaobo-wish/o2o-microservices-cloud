### 1.项目简介

云岚到家是一个本地生活服务平台，对标家政版的美团，用户可以通过平台在线预约家政上门服务。

**运维视角**：平台涉及用户下单、支付、服务人员接单、上门服务、结算分账，每一笔交易背后都有多个微服务在协作。运维的核心工作就是确保整条链路稳定可靠。

| 对比     | 说明                                                         |
| :------- | :----------------------------------------------------------- |
| 单体架构 | 所有业务模块全部在一个项目、一个工程里，打成一个 war/jar 包，部署一套进程 |
| 微服务   | 按业务领域拆分，每个业务独立工程、独立进程，各自部署         |

**为什么使用微服务**：云岚到家业务模块多、角色多、流程长，单体架构会带来代码膨胀、扩展困难、故障扩散、团队协作冲突等问题。微服务把每个业务模块拆成独立服务，各自部署、各自扩容、故障隔离。



### 2.Nacos

Nacos是阿里巴巴开源的一个动态服务发现，配置管理和服务管理平台。是Naming and Configuration Service的缩写，核心作用是解决微服务架构中“服务如何找到彼此”以及“配置如何统一管理”，解决了微服务拆开后最头疼的两个问题。

```properties
1.服务注册与发现

这是微服务之间找到对方的机制。服务实例启动时把自己的地址(IP，端口)注册到Nacos，服务消费者要调用其他服务时，问Nacos要一份可用的实例列表，消费者再从中选择一个。

#服务消费者 = 主动调用其他服务的那个服务。

2.动态配置管理

将配置从代码里剥离出来，集中放到Nacos上管理。改配置时在 Nacos 界面改一下，应用不用重启就能生效。还支持版本管理、灰度发布、一键回滚等功能
#这类的配置主要是经常变的动态调整的，比如数据库地址等
#Nacos 界面就是 Nacos 自带的一个 Web 控制台，你通过浏览器访问它，就能可视化管理配置和服务。它是 Nacos 服务端的一部分，部署完 Nacos 后就能访问。
```

---

工作原理：注册和发现怎么跑的

```properties
服务注册：服务提供者启动时，会向 Nacos 发送注册请求，带上自己的服务名、IP、端口等信息。Nacos 保存下来，之后服务提供者会定期发送**心跳**来证明自己还活着。如果 Nacos 长时间收不到心跳，就会把这个实例从列表里剔除。

服务发现：服务消费者需要调用某个服务时，向 Nacos 发起查询，Nacos 返回该服务的健康实例列表。消费者拿到列表后，自己通过负载均衡算法挑一个去调用（这叫客户端负载均衡）。如果服务列表有变化，Nacos 会主动通知消费者更新。

配置管理：客户端会通过长轮询的方式向 Nacos 请求配置更新。如果配置没有变化，请求会挂起等待一段时间再返回；一旦配置变了，Nacos 会立即把新配置推送给客户端。

#Nacos是配置中心服务端，它负责管理和分发配置，主动来Nacos拿去配置的服务就是客户端。
```

每个微服务的pom.xml都会配置nacos-client这个jar依赖，负责与Nacos服务端通信

长轮询就是：客户端向Nacos发送长轮询请求问我关心的配置变了吗，Nacos不会立刻返回，而是将请求hold住，在这期间变了就返回，然后客户端去拉取新配置。没变超时就循环往复。

```properties
注意！！
Nacos的定位是配置中心，是管理的，但是配置数据持久化的任务是依靠外接数据库MySQL
┌──────────────┐         ┌──────────────┐         ┌──────────────────┐
│ 微服务        │  读写   │    Nacos     │  读写   │     MySQL        │
│ (Nacos客户端) │ ◀────▶ │  (配置中心)   │ ◀────▶ │  db_nacos_config │
└──────────────┘         └──────────────┘         └──────────────────┘
                                                          ▲
                                                     配置真正存在这里
微服务：以为配置在 Nacos 里。

Nacos：对外提供配置读写接口，对内把数据存到 MySQL。

MySQL：config_info 等表里，才是配置真正落地的地方。
```

```properties
## 为什么 Nacos 要外接 MySQL

因为 Nacos 默认用内置的 **Derby** 数据库，但 Derby 有几个问题：

- 每个 Nacos 实例各存各的，**多副本无法共享**。
- 数据在容器里，Pod 一重建就丢。
- 不适合生产环境。

所以生产上必须外接 MySQL，让**配置数据独立、持久、可备份、多实例共享**。
```



### 3.RabbitMQ兔子消息队列

它是一个开源的消息中间件，基于AMQP（Advanced Message Queuing Protocol，高级消息队列协议），它的作用是让一个服务把消息发给另外一个服务，但不需要等待对方立即处理。核心价值就是解耦，异步，削峰，可靠。

| **耦合太紧**（解耦） | 下单后要发短信、加积分、更新库存，全写成同步调用，一个挂了全挂 | 下单只发一条消息，其他服务各自订阅处理  |
| -------------------- | ------------------------------------------------------------ | --------------------------------------- |
| **响应太慢**（异步） | 用户下单要等所有后续操作完成才返回                           | 下单主流程走完就返回，后续异步处理      |
| **流量突增**（削峰） | 秒杀时大量请求打垮下游                                       | 消息先入队，下游按自己能力慢慢消费      |
| **失败重试**（可靠） | 调用失败要手动重试                                           | 消息可持久化，消费失败可重试/进死信队列 |

```
生产者不直接发到队列，而是发到交换机，交换机再根据规则路由到队列。这是 RabbitMQ 和很多其他 MQ 的区别。
生产者(Producer) → 交换机(Exchange) → 队列(Queue) → 消费者(Consumer)
                         │
                    绑定(Binding) + 路由键(Routing Key)           
```



### 4.Elasticsearch弹性搜索

Elasticsearch 是一个开源的**分布式搜索和分析引擎**，相比 MySQL 的 LIKE 模糊查询（全表扫描、无法分词），ES 支持分词、词序、同义词、错别字容错等检索能力。核心概念包括索引、文档、字段、分片、副本、节点、集群，可通过 RESTful API 完成索引的创建、查看与删除。

- **ES**：专门做**全文检索**，像百度一样按关键词搜，毫秒级返回。

快的原因：倒排--词 → 出现在哪些文档。



### 5.Canal订阅与消费组件

Canal 是阿里开源的一个**基于 MySQL 数据库增量日志（binlog）解析**的工具，主要用于**数据库实时同步**。，核心作用是：**伪装成 MySQL 的从库，实时读取 MySQL 的 Binlog，把数据变更解析出来，供下游（ES / Redis / RabbitMQ / 业务）消费。**

它就是把 MySQL 的数据变更**同步到 ES / Redis** 的那座桥。

canal订阅Binlog，对业务无侵入，实现解耦。

canal工作的前提是binlog开启ROW模式，记的是每行变更前后的完整数据，Canal 能准确解析

canal组成：

| 组件             | 作用                                     |
| :--------------- | :--------------------------------------- |
| **Canal Server** | 核心，连 MySQL、拉 Binlog、解析          |
| **Canal Client** | 消费 Canal Server 解析出的数据，写到下游 |
| **Instance**     | 一个 Canal 实例对应一个 MySQL 实例的订阅 |
| **Meta 管理**    | 记录消费到哪个 Binlog 位置，断点续传     |



## 6.Sentinel

**Sentinel** 是微服务架构里负责**流量控制、熔断降级、系统保护**的组件。在 Spring Cloud Alibaba 体系里，它和 Nacos 是搭档——Nacos 管“找到服务”，Sentinel 管“别被流量打死”。

| 风险           | 场景                                        | Sentinel 的作用          |
| :------------- | :------------------------------------------ | :----------------------- |
| **流量突增**   | 秒杀、活动，请求打满                        | 限流，超出的直接拒绝     |
| **服务雪崩**   | A 调 B，B 卡住，A 的线程被耗尽，连带 A 也挂 | 熔断，快速失败，不再等 B |
| **不稳定调用** | 下游偶尔超时、报错                          | 降级，返回兜底结果       |
| **系统过载**   | 整体负载太高                                | 系统自适应保护           |

**核心目标**：当某个环节出问题时，**把故障控制在一定范围，不让它扩散到整个系统**。

sentinel有四个核心概念：资源，规则，熔断机状态机，控制台dashboard

规则有两种存放位置：内存，在每个微服务的JVM里，业务pod重启就丢；外部数据源nacos，可以持久

**默认情况**：你在 Sentinel Dashboard 上配一条限流规则，Dashboard 是通过 HTTP 把规则**推送给各个微服务的 JVM**，规则存在**微服务的内存里**。

注意sentinel有两种形态

| 部分                   | 形态                                                         | 是否独立 Pod                 |
| :--------------------- | :----------------------------------------------------------- | :--------------------------- |
| **Sentinel 核心**      | java依赖包的形式嵌入微服务的JVM中                            | ❌ 嵌在微服务进程里，不是 Pod |
| **Sentinel Dashboard** | 独立 Java 应用，web控制台，用来可视化配置规则，看流量，需要单独部署 | ✅ 是一个 Pod                 |

**JVM（Java Virtual Machine，Java 虚拟机）** 是运行 Java 程序的“虚拟计算机”。你写的 `.java` 代码编译成 `.class` 字节码后，就是靠 JVM 来执行的。JVM实现一次编写到处运行，字节码屏蔽了底层操作系统的差异。



## 7.微服务与组件的区别

组件：MySQL、Canal、Nacos、RabbitMQ、Redis、ES，它们是应用运行时所依赖的外部组件，基础设施。是工具

微服务： 一个独立部署、独立运行、只负责一块业务的小型应用。在这个项目中每个微服务都是一个独立的Java进程，是业务代码。

他们都是k8s集群中的Pod，但是角色完全不同

|            | 微服务 Pod         | 基础设施 Pod                |
| :--------- | :----------------- | --------------------------- |
| 镜像       | 你自己打的业务镜像 | 官方镜像（mysql、nacos 等） |
| 代码       | 开发写的           | 开源代码                    |
| 挂了的影响 | 该业务不可用       | 依赖它的微服务受影响        |
| 数量       | 多，按业务拆       | 少，通常一个中间件一套      |

```
微服务 ──依赖──▶ MySQL、Redis、RabbitMQ、Nacos、ES
                    ▲
                    │
              Canal ─┘（Canal 依赖 MySQL，同步给 ES）
```

生命周期

|          | 微服务               | 基础设施                 |
| :------- | :------------------- | ------------------------ |
| 启动频率 | 高，经常发版、扩缩容 | 低，部署后长期运行       |
| 重启影响 | 该业务短暂不可用     | 依赖它的所有微服务受影响 |
| 升级方式 | 滚动更新，频繁       | 谨慎升级，影响面大       |
| 数据     | 无状态（大部分）     | 有状态（存数据）         |

```
**Gateway 是微服务**（你部署的一个应用），但它**扮演基础设施的角色**（统一入口）。它是“微服务形态的基础设施”。
```

**业务服务（微服务）和基础设施服务（中间件）是两回事。**



## 8.XXL-JOB

XXL-JOB 是一个开源的**分布式任务调度平台**，其核心设计理念是“调度”与“任务”解耦，通过一个独立的调度中心来统一管理分布式的执行器。相比 Spring @Scheduled 或 Quartz，它解决了集群环境下任务重复执行、管理不便等问题，让开发者能快速上手并专注于业务逻辑。

##### 1.核心架构

**调度中心 (xxl-job-admin)**：这是一个独立的 Web 应用，充当“大脑”的角色。它负责统一管理任务、触发调度、提供可视化界面（任务的增删改查、启停、日志查看等）。调度中心支持集群部署以保证高可用。

**执行器 (xxl-job-executor)**：这是嵌入在你业务项目中的模块，充当“四肢”。它负责接收调度中心的指令并执行具体的任务逻辑。你只需要在业务代码中编写一个方法并加上 `@XxlJob` 注解，它就能被调度中心管理

##### 2.工作流程

1. 调度中心（Admin）定义任务（如：每30分钟执行一次）
2. 调度中心触发任务，发送给注册的执行器
3. 执行器执行具体逻辑（如：扫描超时订单）
4. 执行结果回调给调度中心，记录执行日志

##### 3.优点

```
- 简单易用：通过 Web 页面操作，一分钟即可上手。支持动态修改任务状态和参数，即时生效，无需重启服务。
- 高可用与弹性：调度中心和执行器均支持集群部署。执行器支持自动注册与发现，并具备弹性扩容缩容能力，新机器上线或下线后，下次调度会自动重新分配任务。
- 丰富的调度策略：
  - 触发策略：支持 Cron、固定间隔、固定延时、API 触发、人工触发、父子任务触发等。
  - 路由策略：当执行器集群部署时，支持第一个、轮询、随机、一致性HASH、故障转移等多种路由算法，决定任务发给哪台机器执行。
- 完善的容错机制：
  - 阻塞处理策略：当调度过密时，可选择“单机串行”（默认）、“丢弃后续调度”或“覆盖之前调度”。
  - 任务超时控制：可自定义超时时间，到时主动中断任务。
  - 失败重试与告警：支持失败自动重试，并默认提供邮件告警，同时预留了扩展接口（如短信、钉钉）。
- 强大的任务管理：
  - GLUE 模式：提供 Web IDE，支持在线编辑任务代码（如 Shell、Python），动态发布，无需部署。
  - 分片广播：一次调度可触发集群中所有执行器执行，支持大数据量并行处理。
  - 实时日志：支持在线以 Rolling 方式实时查看执行器的完整执行日志
```
